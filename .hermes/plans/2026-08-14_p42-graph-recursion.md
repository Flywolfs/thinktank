# P4.2 知识图谱递归扩展 — 设计文档

> 日期: 2026-08-14
> 状态: 设计已确认，待实现

## 一、目标

批准建图后，图谱里的关联实体可以触发新一轮调查（图谱驱动调查，不是每次从实体名开始）。
核心约束（用户确认）:
1. **控制权在用户**，系统只做引导（方案 B+D：用户驱动 + 建议式）
2. **闭环必须正确**：A→B→C→A 时 A 是同一个节点，不无限延伸、不重复实体
3. **上下文继承**：新调查带血统（父调查 + 关系），不是空白重挖

## 二、核心决策记录

### 2.1 为什么存储层天然防重复（用户提问，已澄清）

| 层 | 机制 | 是否去重 |
|----|------|----------|
| Neo4j 存储 | `MERGE (e:Entity {name})` + `MERGE (a)-[r]->(b)` | ✅ 天然 |
| get_subgraph 查询 | `RETURN DISTINCT n.name` + Python `entities[name]=` dict 键 | ✅ 天然 |
| 前端渲染 | ECharts `entities.map(...)` 未显式去重 | ⚠️ 上游已保证唯一，防御性补一道 |

**结论**：闭环 A→B→C→A 在 Neo4j 中 A 只有一个节点，C→A 的 MERGE 指向原 A。前端显示的就是图谱存的，不会出现两个 A。

### 2.2 防环状态机（用户方案确认：visited 剪枝 + 分级）

用户提出: A→B→A 时停止搜 A，转搜 C（DFS 顺序）。确认本质是 visited 剪枝，但有 3 个漏洞要补:

```
发起深挖目标 X 前:
  1. X 已调查过?
     ├─ 否 → 正常发起（记录 parent_job_id 血统）
     └─ 是 → 前端黄色标记「已挖过 · N 次」
            ├─ 用户确认重挖 → 发起（investigated_count+1）
            └─ 系统自动判断（见 2.3）或跳过
  2. X 是当前调查链祖先（A→B→X=A）?
     └─ 是 → 提示「形成闭环」，默认不发起（除非系统判断强新线索或用户强制）
```

漏洞及对策:
1. **停止的是"新调查"不是"丢弃信息"** → B 调查中发现的 A 的新证据照常入库，investigated 只控制是否再以 A 为核心发起新调查
2. **visited 匹配基于实体归一化** → 见 2.4，别名/错别字/简繁体防绕过
3. **一刀切不挖丢机会** → 分级（未调查/浅查/深查），系统自动判断重挖（2.3）

### 2.3 系统自动判断重挖（用户确认：默认系统自己决定 + 前端开关）

```
前端发起深挖时开关（默认开）:
  🔁 遇到成环时由系统决定是否重挖
    系统判断逻辑:
      新线索强度 > 阈值 且 上次调查较浅 → 自动重挖（标记"自动重挖·证据增强"）
      否则 → 跳过，提示「已调查，新线索不足」
  [关] → 每次撞回都停下问用户

硬上限: 同一实体最多 3 次自动重挖，超过必须用户手动确认
留痕: investigated_count 递增 + 图谱显示第 N 次调查证据
```

强新线索评分（系统）:
- 新调查中**提到 X 的结果条数**
- 涉及 X 的**新关系类型数**
- 与旧调查发现的**重叠度低**

### 2.4 实体名称归一化（中文/英文分流）

```
原始 name → 语言检测 → 中文: 全半角 → 去后缀(有限公司/集团/工作室) → 转简体(zhconv/OpenCC) → 别名表
                      → 英文: lowercase → NFKC(unicodedata) → 去冠词/后缀(Inc/Ltd/Corp) → 复数词干化 → 别名表
                      → 归一化 key
入库: merge_entity(归一化 key, 原始 name 存 alias 字段)
visited 检查: 用归一化 key 比较
```

别名表**增量学习**：新调查实体入库时，若 LLM 判定与已有实体同指，自动把新 name 加入该实体 alias 列表（归一化 key 不变）。图谱越用越准。

### 2.5 强新线索 UI 体现（用户提问）

```
① 图谱节点角标:  A 节点加「证据增量」标记 (🔶 悬停显示新线索数/强度)
② 调查链导航条:  蒋方舟 → 韩寒 →（发现）→ 蒋方舟 🔶  高亮闭环+新线索
③ 建议区:        💡 建议重挖「蒋方舟」— 韩寒调查发现其资助方线索 [一键重挖] [忽略]
```

### 2.6 关系文字漂移处理（已确认 2026-08-15）

两次调查用不同词描述同一关系（"同代作家" vs "朋友"）→ 不同 rel_type → 平行边。
**确认方案：重挖复用旧 rel_type + 证据累积（不新增边）**

```
重挖 A 产生新发现: (A) -[朋友]-> (B)     ← LLM 用的新文字

检测: A→B 已有同向边吗？
  ├─ 有 → 不建新边，把新证据「填进」旧边（MERGE ON MATCH 分支）:
  │       relation: 保留旧文字（或归一化规范名）
  │       evidence_count: N → N+1        ← 证据次数递增
  │       sources: 追加本次调查 job_id / URL
  │       new_finding: 覆盖为最近一次新增证据摘要
  │       last_seen: 更新为本次调查时间
  └─ 无 → 新建边（evidence_count=1）
```

关键规则:
1. **同向边判定**：`(A)-[rel]->(B)` 方向一致才合并；反向 `(B)-[rel]->(A)` 是不同语义，允许新建
2. **语义判定分层**：
   - rel_type 相同 → 必合并（硬规则）
   - rel_type 不同但 LLM 判定同义（朋友/同窗/同代作家 → 社交关系）→ 合并 + 更新规范 rel_type
   - LLM 判定不同义（朋友 vs 资助方）→ **新建边**（不同真实关系，必须保留）
   - **默认保守：LLM 不确定 → 新建边**（宁可多一条边也不丢语义）
3. **new_finding 只记最近一次证据点**（一句话摘要 + 来源），历史证据在 sources 数组，计数在 evidence_count
4. **多语义关系各自成边**：A 既是 B 的朋友又是 B 的资助人 → 图谱上两条边，各自累积证据（不能合并成一条，那是错误做法）
5. **本质是 MERGE ON MATCH**：现有 merge_relation 已 SET last_seen，只需补 evidence_count 递增 + sources 追加

## 四、验收标准

1. A→B→C→A: 图谱 A 只有一个节点，C→A 边指向原 A，无重复实体
2. 深挖已调查实体: 显示「已挖过·N次」标记，默认系统判断是否重挖
3. 系统自动重挖: 只在强新线索时发生，3 次上限后必须人工
4. 中文"臺灣/台湾"、英文"MICHAEL/michael"归一为同一节点
5. 新调查继承血统: job.parent_job_id + parent_relation 可回溯
6. 前端: 角标/血统链/建议区/开关全部可用
